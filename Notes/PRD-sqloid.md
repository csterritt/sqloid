# PRD: Sqloid v1

## Problem Statement

Inspecting and querying a SQLite database currently means dropping down to the `sqlite3` shell or an external GUI. The shell demands that every query be typed out by hand, column names memorised, and results are hard to read, page through, or export. There is no lightweight, keyboard-driven tool that lets a developer explore a database's schema, build common queries interactively, view results in a scrollable grid, and export them — whether the database is a plain SQLite file or a local Cloudflare D1 database created by wrangler/miniflare.

## Solution

Sqloid v1 is a terminal UI application (single user, single developer — meaning no authentication, collaboration, or server behaviour) that opens a SQLite database — either given explicitly on the command line, or discovered in a local wrangler D1 state directory — and presents a full-screen interface: results occupy most of the screen, and a query-builder bar sits at the bottom.

The original project vision was a general SQL editor in which the user types SQL commands. For v1 this is deliberately narrowed to a structured query builder / data browser: guided selection, deterministic value parsing, and safe parameter binding remove the need to memorise schemas while keeping free-text SQL entry deferred to a post-v1 advanced mode. No column-type filtering or type-specific input hints are required in v1.

The user builds SELECT, UPDATE, DELETE, and INSERT queries by stepping through fields: command, table, column(s), where, group by, order by, and limit. Values use universal text entry with deterministic parse-and-bind coercion. Queries run with Enter. SELECT results appear in a frozen-header grid with serialized vertical paging, horizontal scrolling, and an independently read count. In-session query and result histories each retain the 20 most recent entries. Queries and results can be exported to `.sql`, CSV, or JSON files.

## Query Grammar (v1)

Sqloid v1 is a **builder for a subset of SQL**, not a full query engine:

- **SELECT**: `SELECT <projection> FROM <table> [WHERE <predicate>] [GROUP BY <column, ...>] [ORDER BY <column-or-aggregate> [ASC|DESC]] [LIMIT <n>]`.
  - A projection is either the sole wildcard `*`, or an ordered list of entries `(column, aggregate?)`, where aggregate is empty (`Value`) or one of {Count, Min, Max, Avg, Sum}. Different aggregates on one column may coexist; an identical pair is not added twice.
  - In an empty Column(s) popup, `*` is the default-selected first item and the synthetic `COUNT(*)` item is immediately below it. `COUNT(*)` appears only while the projection is empty. Selecting it adds the sentinel directly, without opening the named-column aggregate popup, and reopens Column(s). It can coexist with subsequently selected aggregate entries. Removing entries back to empty makes it reappear. Named columns always continue to the aggregate popup. `MIN(*)`, `MAX(*)`, `AVG(*)`, and `SUM(*)` are never offered.
  - Selecting wildcard clears prior entries and makes it the sole entry. Removing an entry removes the most recently added one; reordering is unsupported.
- **WHERE (SELECT/UPDATE/DELETE)**: zero or one predicate `<column> <operator> <value>`, with operator from {`=`, `!=`, `<`, `<=`, `>`, `>=`, `IS NULL`, `IS NOT NULL`, `LIKE`}. All operators are offered for all columns. Null operators take no value. A user-entered token spelled `NULL` remains TEXT under universal parsing; the value prompt shows an inline hint and contextual help says to use `IS NULL`/`IS NOT NULL` for SQL null and that ordinary comparisons and LIKE do not match actual NULL values. AND/OR, parentheses, and IN are unsupported.
- **GROUP BY**: assisted multi-select of table columns; duplicates are prevented and empty means no GROUP BY. In every query that has GROUP BY, every nonaggregate projected column must be grouped. Wildcard with GROUP BY is prohibited. Mixed aggregate/nonaggregate projection without GROUP BY is invalid. All-aggregate projection without GROUP BY is valid.
- **ORDER BY**: one column/expression with direction defaulting to ASC. Aggregate/grouped queries offer only grouped columns and selected aggregate entries.
- **LIMIT**: integer 1 through 9,223,372,036,854,775,807. Zero, malformed input, and overflow are invalid; empty means an unbounded logical result.
- **UPDATE**: `UPDATE <table> SET <column> = <assignment>, ... [WHERE <predicate>]`; one or more unique SET columns are required. Each assignment has exactly one choice from {Value, NULL}: Value opens universal text entry, binds the parsed value, and is complete only after entry is submitted; NULL emits the SQL keyword `NULL` and adds no parameter. Default/Omit is never offered for UPDATE. SQL parameters are ordered first by Value assignments in SET-column order, skipping NULL assignments, and then by the optional WHERE value.
- **DELETE**: `DELETE FROM <table> [WHERE <predicate>]`.
- **INSERT**: `INSERT INTO <table> (<column>, ...) VALUES (<value>, ...)`; each insertable column is Value, NULL, or Default/Omit. If all are omitted, emit `INSERT INTO "table" DEFAULT VALUES`. INSERT has no WHERE/GROUP BY/ORDER BY/LIMIT.

LIKE values are bound verbatim: `%` and `_` retain SQLite wildcard meaning, with no v1 escape mechanism. Case behaviour is SQLite's default and unrelated to case-insensitive popup search. Joins, subqueries, expressions, IN, HAVING, and multiple predicates are out of scope.

## Runnable-State Contract

QueryBuilder data validity and UI context gates are separate. A state is data-runnable only when the following authoritative prerequisites hold; Enter executes only when it is also in a base context with no overlay or focused text/search input, no request is in flight, and the screen is large enough.

| Command | Required data | Command-specific validity | Common gates |
|---|---|---|---|
| SELECT | Eligible table; nonempty projection | Valid WHERE and Limit; every grouped nonaggregate is grouped; wildcard not grouped; mixed aggregate/nonaggregate without GROUP BY invalid; all-aggregate without GROUP BY valid; valid grouped ORDER BY | Selected command; all identifiers still exist in refreshed schema; no incomplete value prompt |
| UPDATE | Eligible table; at least one SET assignment; every SET {Value, NULL} choice complete and every Value entry submitted | Optional WHERE complete; SET columns unique | Same common gates; destructive pre-execution workflow required |
| DELETE | Eligible table | Optional WHERE complete | Same common gates; destructive pre-execution workflow required |
| INSERT | Eligible table with at least one insertable column; every prompted column complete | Each column has exactly one Value/NULL/Default choice; all-omit is valid and emits `DEFAULT VALUES`; a zero-insertable-column table is never runnable | Same common gates |

When Enter is attempted on invalid data, execution does not start: focus moves to the first invalid field in visual order and a specific inline reason is shown. An invalid UI context consumes Enter according to that context instead. Enter on otherwise runnable data first starts the cancellable pre-execution schema validation defined below; actual execution begins only after that validation succeeds.

## Builder and Display Interaction

- Choosing S/U/D/I on the Command field immediately selects/replaces the command and advances to Table. A command change retains the table only if it remains eligible, clears all downstream command-specific state, and focuses the first newly required field; switching a selected view to a write command clears Table.
- The refreshed Table popup and searchable column/GROUP BY/ORDER BY popups use case-insensitive subsequence matching: empty search shows all, no match keeps the popup open with `no matches`, and changing search resets its highlighted selection. Aggregate and operator popups are scroll-only. Single-select Enter accepts; multi-select Enter adds and reopens; Esc preserves only already completed multi-selections.
- WHERE guides column → operator → value and shows the SQL-NULL hint at value entry. UPDATE guides SET multi-selection → one {Value, NULL} choice per selected column, with universal entry for Value only → optional WHERE. INSERT guides one {Value, NULL, Default/Omit} choice per insertable column. Shift+Tab/arrows can revisit UPDATE/INSERT prompts with prior choices and values restored exactly.
- Left/Right and Tab/Shift+Tab move builder focus. Up/Down only moves popup selection or toggles ORDER BY direction in its base field. Backspace/Delete removes the most recent projection entry or clears the focused whole-value field as appropriate.
- The grid freezes its deduplicated header, shows the displayed absolute range and independent result-count status, and horizontally tracks a first-visible result-column index. Shift+Page Down and `.` advance exactly one result column; Shift+Page Up and `,` retreat exactly one; boundaries are no-ops. Widths are recomputed from the new first column, an oversized column is capped and ellipsized without intra-cell scrolling, and resize preserves then clamps the first-column index. Empty SELECTs show an explicit `No rows` result rather than a blank grid. Query/write errors replace the result view but older results remain available after finalization.
- Ctrl+P/N walks query history and restores complete builder state without mutating history. Ctrl+E/Y enters result history and views immutable snapshots without re-fetching. UPDATE/DELETE summaries show statement `RowsAffected()` and INSERT shows rows added, each with its executed query; those labels never imply persistence when the transaction outcome is unknown.

## Execution and Result Lifecycle

### Identities and state

An **active SELECT** is distinct from a **request in flight**. It can remain active between requests and own future page requests. Every actual SELECT or write execution has an execution ID. Each database request also has a request ID; page requests include a viewport generation. Resizing or deactivating/finalizing a SELECT advances the relevant generation. A response may mutate UI/cache only if its execution, request, and generation are current.

Destructive estimation and schema validation are **pre-execution workflows**, not executions. Each has its own preparation/request identity. Opening either appends neither query nor result history. Schema validation first reads `PRAGMA schema_version`; an unchanged version uses the schema cache, while a changed version refreshes the selected object and columns and revalidates object/column eligibility, identifiers, insertability, and rowid properties. Invalidated data clears only dependent builder state and focuses the first specific reason. Refresh failure blocks execution with a visibly stale notice and retry/cancel; failed or Ctrl+W-cancelled validation creates no query or result history. Path deletion or replacement takes terminal precedence. Actual execution and history append occur only after successful validation; a post-validation DDL race is an ordinary execution error.

Destructive preparation then has phases `estimating` and `awaiting-confirmation`. Esc, Ctrl+W while estimating, or any dismissal cancels preparation and creates no history. Confirming starts the sole actual write execution, appends query history subject only to consecutive-identical suppression, and ultimately creates exactly one result entry.

Every running request uses a cancellable context on its own dedicated leased connection. Ctrl+W transitions visible state to `cancelling…`, invokes connection-scoped SQLite interrupt semantics, and starts no replacement request until the cancelled request settles. A success arriving after cancellation was requested is discarded and classified as cancelled. Connections are not force-closed. A controlled CPU-bound query must settle within one second of cancellation; cancellation while waiting on a lock must settle no later than the five-second busy timeout. Independent requests are cancelled independently and a subsequent request on the connection is unaffected.

An **accepted quit** occurs only after confirmation in every nonterminal context. During pre-execution validation/preparation it requests cancellation, waits for settlement, and exits without appending either history. During an active SELECT it cancels and settles pending requests, finalizes the SELECT once under its cancellation/success state, and exits; an idle active SELECT finalizes directly. During a write it follows the commit-boundary rules below. Cleanup is never abandoned.

### SELECT

1. After successful pre-execution schema validation, Enter starts one SELECT execution and appends query history unless it is identical to the immediately preceding execution. Its first page and complete-result count are launched concurrently on two distinct dedicated leased connections in both WAL and rollback-journal modes; the pool is configured with at least and at most two appropriate database connections. Sqloid neither changes journal mode nor silently serializes these reads. They may observe different committed states, and an external writer may delay or error either read.
2. At most the count request and one page request may coexist. All page requests, including the first and later navigation, are serialized. Page Up/Down is ignored while a page request is pending, with visible loading feedback. Horizontal scrolling remains local. A replacement page/count request cannot start until its predecessor has settled after cancellation.
3. Ctrl+W cancels all active requests for the active SELECT, including a later page-only request, through their independent connection-scoped interrupts. Late responses from a cancelled old execution are discarded and classified cancelled even after a newer execution begins.
4. Resize invalidates the pending page request's viewport generation. Its stale response is rejected; after cancellation/settlement, the required page for the new exact page size is fetched. Entering result history or otherwise finalizing/deactivating also rejects late page responses.
5. Count failure does not end successful paging. The header changes from `Counting rows...` to `Count unavailable`; it never represents the count as an exact shared snapshot or clamps displayed/cached rows to an inconsistent count.
6. A SELECT is finalized only by: starting an actual new execution (opening an estimate is not enough), entering result history, cancellation or failure that ends the SELECT, or an accepted quit. Builder editing/focus, popups, help, save flow, write estimation, query-history browsing/restoration, resize, result export/copy, and idle periods do not finalize it.
7. Finalization creates exactly one immutable result-history entry for that execution. Success, count failure with rows, partial page failure, and cancellation after rows retain the captured rows and metadata. Cancellation before rows creates a non-tabular Cancelled entry; first-page failure creates an error entry. There is no additional entry for each page or count request.

History entries have stable IDs. Starting an actual execution while viewing either history first exits history. Normal pending restrictions therefore prevent execution from evicting the visibly selected entry. Defensively, if an externally driven append evicts the selected entry, selection moves to the new oldest remaining entry with `Previously viewed result was evicted from history`; an empty history returns to the base view. Query-history cursors follow the same stable-ID/eviction behavior, and the UI never displays rows whose backing entry was evicted.

### Cache and snapshot invariant

The active cache is one contiguous inclusive range of **absolute logical row positions**, capped independently at 10,000 positions and 64 MiB of retained payload. Duplicate-valued rows remain separate positions. Payload accounting is raw TEXT/BLOB byte length, 8 bytes per INTEGER/REAL, and 0 for NULL, excluding model overhead and metadata.

- A forward adjacent page appends/replaces overlap and evicts the low end; a backward adjacent page prepends/replaces overlap and evicts the high end. Incoming adjacent pages evict the standard opposite end until both caps hold.
- Overlap replaces the same logical positions and never duplicates them. A stale response whose requested range is nonadjacent to the current retained range after accounting for overlap is rejected rather than creating a gap.
- Byte-cap eviction records `truncated-by-byte-cap`; the results header and export flow show exactly `Result truncated: 64 MiB cache limit`. If the retained rows from one fetched page exceed 64 MiB, retain only complete leading rows that fit, stop at the first nonfitting logical position, never retain a partial row, and show `result page exceeds the 64 MiB v1 limit at row N`. If one row/value exceeds the connection-local limit, show `result value exceeds the 64 MiB v1 limit at row N`. In both failures, `N` is the one-based logical result position and the result view identifies the page as failed there.
- Snapshot/export rows are ordered by ascending logical position, regardless of traversal order. BLOB bytes are retained and exported exactly and displayed as `[BLOB n bytes]`; fetching is eager but bounded by these limits, not a streaming LOB browser.
- Metadata records retained start/end, optional known total, reached-low/reached-high endpoints, whether row- or byte-cap eviction occurred, a **completeness status**, and a separate **terminal outcome**. Completeness uses `complete`, `partial`, and `truncated` labels: `complete` is exclusive and requires both logical endpoints known plus the entire limited logical result retained; rows beyond the user's Limit are irrelevant. `truncated` means known or observed rows were evicted or exceed the retained range; `partial` means unseen rows within the limited logical result may remain or count/page work did not finish. Incomplete snapshots retain both labels when truthful. Terminal outcome is independently `success`, `cancelled`, or `failed`, with cancellation/failure reason and last failure position where applicable.
- If count failed or is unavailable, an observed short or empty final page establishes the high endpoint. Otherwise the total remains unknown and the snapshot is partial unless both endpoints are established by observation. Count/cache inconsistencies are not clamped.

### Writes and commit boundary

INSERT starts its actual execution directly. UPDATE/DELETE follow `builder → estimating → awaiting-confirmation → beginning → executing → rollback-cleanup or committing → committed/failed/cancelled/outcome-unknown`.

- `beginning` and `executing` are cancellable through the leased write connection. An atomic cancellation check occurs after statement completion and immediately before beginning COMMIT; the cancellation flag wins even if the statement returned success. Cancellation or statement failure initiates rollback cleanup. After the commit boundary no interrupt is issued.
- Rollback cleanup and `committing` are noncancellable. Ctrl+W after the commit boundary is ignored with `Commit in progress; cancellation is no longer available` feedback.
- A cancellation or statement failure guarantees the database is untouched only after rollback is confirmed successful. A successful commit yields one write summary entry. Each actual write produces exactly one result entry.
- If rollback or commit cannot be resolved, the result is **outcome unknown**. The application waits until no transaction or driver work remains pending, creates the newest non-tabular result entry, selects it initially, and then enters the outcome-unknown terminal result view. The entry contains status, operation/table, SQL, commit-versus-rollback phase, driver error, and optional statement `RowsAffected()` explicitly labeled as not proving persistence. The state forbids further database work but preserves in-memory query/result selection and query saving; Ctrl+E/Y navigates entries, Ctrl+S saves SQL, and Ctrl+X reports `selected result has no tabular data to export` without opening a picker.
- An accepted quit while a write is cancellable requests cancellation and waits for rollback resolution. An accepted quit while committing waits for commit resolution. It never tears down the process while transaction/driver work remains pending; only after resolution, or after pending work has ended with an unknown outcome, does quit complete.

## Global Key Precedence and Context/Action Matrix

Precedence is: **terminal state → quit confirmation → top overlay → focused text/search input → request-in-flight restrictions → base context**. A higher level consumes the key before lower levels.

- In every nonterminal enabled context, both `q` and Ctrl+C open the same quit confirmation, suspending the exact current context (focus, overlay, popup search, picker/save state, active SELECT, viewport, and preparation state). Ctrl+C in quit confirmation confirms quit. Esc/n cancels quit with no key leakage and restores that exact suspended context and focus. An awaiting estimate restores its retained result and confirmation-enabled state; an in-flight estimate may settle behind quit and restoration shows its latest settled state. An overwrite confirmation restores destination, format, immutable copy, and selection; cancelling overwrite afterward returns to the intact save-flow path. Confirmed quit performs the lifecycle cleanup before exit.
- In terminal states, terminal rules override all others. In ordinary UI, Esc cancels only the top overlay and restores its opener's exact focus/state. Modals do not stack, except that quit temporarily suspends one overlay.
- `?` inserts a literal question mark in focused text or popup/file-picker search input. It opens contextual help only in base contexts. Help Esc returns exact prior focus.
- Base actions are available only with no overlay and no focused input/search. Query/result history and Ctrl+S/Ctrl+X are disallowed while any database request is in flight, with explanatory feedback.
- Ctrl+W applies only to cancellable active database requests/phases. Elsewhere it is ignored. It cancels active SELECT count/page requests and cancellable write phases; during commit/rollback cleanup it is ignored with boundary feedback.

| Context | Enter / printable | Esc | Navigation | Ctrl+P/N, Ctrl+E/Y | Ctrl+S / Ctrl+X | Ctrl+W | `?` | `q` / Ctrl+C |
|---|---|---|---|---|---|---|---|---|
| Base builder/result | Enter validates then runs valid state; Command accepts S/U/D/I | Clears displayed error or no-op | Tab/arrows fields; Page Up/Down serialized paging; Shift+Page or `,`/`.` one column | Query/result history when idle | Save/export when idle and target exists | Cancels active request only | Help | `q` and Ctrl+C open quit confirmation |
| Popup | Select/add | Close unchanged or preserve completed multi-selections | Popup Up/Down; printable search where searchable | Disallowed | Disallowed | Cancels request, not popup, only if one exists | Inserts in searchable popup; otherwise no-op | `q` is input in focused search; otherwise `q` and Ctrl+C open quit confirmation |
| Text/search input | Submit value | Restore prior value and focus | Input editing | Disallowed | Disallowed | Cancels request only if one exists | Inserts `?` | `q` inserts; Ctrl+C opens quit confirmation |
| Non-quit modal/overlay, including validation/estimate/confirm/save/overwrite/help | Modal-specific | Cancel top overlay and restore opener | Modal-specific | Disallowed | Disallowed | Validation/estimate/request cancellation only where stated | No-op unless focused search | `q` and Ctrl+C open quit confirmation unless `q` belongs to focused input |
| Quit confirmation | Enter/y/Ctrl+C confirms | Esc/n restores exact suspended context with no leakage | No other action | Disallowed | Disallowed | Disallowed | No-op | `q` no-op |
| Request pending in otherwise base context | Enter ignored with running hint | Base Esc behavior | Page Up/Down ignored while page pending; local one-column horizontal allowed | Disallowed | Disallowed | Cancel if phase cancellable; show `cancelling…` until settlement | Base help only if no input/overlay | `q` and Ctrl+C open quit confirmation |
| Terminal deletion/replacement/outcome-unknown | No DB action | No-op | History selection if available | Allowed for in-memory selection | Ctrl+S from immutable memory; Ctrl+X rejects non-tabular summaries; no work remains pending | No-op | Reduced help | `q` and Ctrl+C exit immediately with status 1 |
| Too-small screen (<80×24) | Other keys ignored | No-op | No-op | Disallowed | Disallowed | Active request cancellation remains available | No-op | `q` and Ctrl+C open quit confirmation |

The too-small screen preserves all application state behind the message. Resize to at least 80×24 restores the exact prior context and focus. In terminal deletion, replacement, and outcome-unknown states, no transaction/driver work remains pending and `q` or Ctrl+C exits immediately with status 1. There is no nonterminal `q` shortcut that skips confirmation.

## Implementation Decisions

- **Language and stack**: Go with pure-Go/no-cgo `modernc.org/sqlite`; Bubble Tea for the TUI, Lip Gloss for styling, Bubbles components where appropriate, and `mow.cli` command-word/argument parsing for `sqlite <file>` and `d1`. Pin an exact vetted modernc version. Release-blocking capability tests must prove dedicated-connection context cancellation and connection-scoped SQLite interrupt behavior; a version that fails must be changed, never silently accepted as best-effort.
- **CLI behavior**: `--help`/`-h` prints usage; `--version`/`-v` prints version; unexpected arguments print a usage error to stderr and exit 2. A directory passed to `sqlite` fails the header validation as `not a SQLite database` and exits 1. A missing sqlite argument is a usage error; validation never creates the target.
- **D1 discovery**: inspect only `.wrangler/state/v3/d1/miniflare-D1DatabaseObject` relative to process working directory; never search recursively or probe alternate layouts. Candidates have case-sensitive `.sqlite` extension and no lowercase `metadata` substring; `-shm`/`-wal` sidecars are ignored. Case sensitivity is deliberate for identical Linux/macOS sets. Exactly one candidate is required. Multiple candidates produce exactly the single line `There is more than one SQLite database in .wrangler` with no layout hint. An absent, unreadable, or candidate-free directory exits 1 with exactly two lines: `no candidate database found in .wrangler`, then `Expected .wrangler/state/v3/d1/miniflare-D1DatabaseObject; your Wrangler version may use a different local-state layout. Use sqloid sqlite <file> to open the database explicitly.`
- **Startup validation and errors**: existence check → readable check → exact 16-byte `SQLite format 3\0` header check → open read-write without creating (`mode=rw`) → harmless `PRAGMA schema_version` probe. Preserve EACCES/EPERM/EROFS classification through wrapping. A mode=rw permission failure is exactly `cannot open database read-write: <path>: permission denied`; EROFS is exactly `cannot open database read-write: <path>: read-only file system`; otherwise include the raw OS/driver cause after the same prefix. Invalid headers and directories remain `not a SQLite database`. Every file-validation/open startup failure prints exactly one stderr line and exits 1; successful startup is silent; D1 no-candidate discovery is the explicitly defined two-line exception. There is no degraded read-only mode.
- **Connection pool, limits, and busy handling**: configure `database/sql` for exactly two appropriate database connections (minimum and maximum two), and lease a distinct connection per concurrent page/count request. Configure the five-second busy timeout on every connection through the supported modernc DSN and/or connection hook, and set connection-local `SQLITE_LIMIT_LENGTH` to exactly 64 MiB on every connection without modifying the file. Startup expiry exits as above; mid-session expiry appears as ordinary `database is locked` request error unless health classification overrides it. Do not set or mutate journal mode.
- **Session health**: no watcher or continuous monitoring. At startup record the original file's device and inode on Linux/macOS. Immediately before every database request—schema validation/refresh, estimate, count, page, or an entire phased write transaction—stat the original path and verify both existence and identity; every newly opened/replacement pooled connection also verifies identity before use. The write transaction is one request, so there is one boundary check before BEGIN and none between statement and COMMIT. Absence, including rename-away, enters terminal deletion `Database file no longer exists — session ended`; identity mismatch enters terminal replacement `Database file was replaced — session ended`. After every request error, repeat the same classification before ordinary error/outcome handling: a raced replacement followed by an error is therefore classified terminal immediately. A replacement race after a successful precheck may let that current request succeed against the already-open original; the next request boundary then detects replacement before more work begins. In-place same-inode mutation follows ordinary SQLite behavior/errors. Idle changes are discovered on the next operation.
- **SQL safety**: user values are bound; identifiers come only from refreshed schema and are double-quoted with embedded quotes doubled. Aggregate and direction values are fixed choices.
- **Numeric value parsing and rendering**: input is verbatim with no trimming; whitespace anywhere makes TEXT. INTEGER matches `-?[0-9]+` and must fit signed 64-bit (leading zeros allowed; leading `+` falls through). Otherwise REAL is any finite value accepted by `strconv.ParseFloat` within float64 (`1.`, `.5`, exponent forms allowed; leading `+` and overflow fall through). Everything else is TEXT verbatim, including typed `NULL`, `NaN`, `Inf`, `0x1A`, and padded strings. SQLite column affinity may coerce bound values. SQL NULL is available only through explicit popup/operator choices; empty input is empty TEXT. BLOB input is unsupported. For every finite REAL returned by SQLite, compute `token = strconv.FormatFloat(v, 'g', -1, 64)` and append `.0` iff the token contains none of `.`, `e`, or `E`; this exact locale-independent token is used in grid, CSV, and raw JSON-number output (for example `1.0`, `-0.0`, `1e+20`). INTEGER formatting remains unchanged. Existing non-finite policy remains separate.
- **Estimate SQL and modal**: the estimate is exactly `SELECT COUNT(*) FROM <quoted target> [WHERE <identical predicate>]`. It binds only WHERE parameters in predicate order, never UPDATE SET parameters, including when SET mixes Value and NULL. It is an independent read labeled `estimated matching target rows`; it excludes trigger side effects and may differ from changed/no-op rows and `RowsAffected()`. The modal opens immediately and continuously displays operation type, table name, rendered write SQL with safely serialized Value literals and `NULL` keywords, and the prominent no-WHERE all-rows warning when applicable. It initially shows `Estimating matching target rows…`, with Enter/y confirmation disabled. When the estimate succeeds it shows the estimate and enables confirmation; when it fails it shows the failure while retaining SQL/warnings and also enables confirmation. Enter/y then confirms the sole actual write; Esc/n dismisses preparation without history. Ctrl+W while estimating shows `cancelling…`, waits for interrupt settlement, and dismisses preparation without history.
- **Write transaction**: Connection explicitly implements beginning/executing, atomic pre-commit cancellation check, noncancellable rollback cleanup/committing, and outcome resolution. It must not report cancelled/failed-and-untouched before rollback is confirmed.
- **Paging consistency**: use LIMIT/OFFSET requests. The complete logical-result count is exactly `SELECT COUNT(*) FROM (<SELECT including the user's LIMIT>)`; rows beyond Limit do not affect completeness. Without user ORDER BY, append `ORDER BY rowid` only for ordinary rowid tables without a declared rowid shadow; no implied stability for views, virtual/WITHOUT ROWID/shadowed, aggregate/grouped, ties, or concurrent writes. Count and page launch concurrently on separate leased connections as independent autocommit reads with no shared snapshot and may drift. The header is exactly `Result count: N`, or `Result count: N (after Limit M)` when Limit is present. Help states that this is the complete limited SELECT result, not table or pre-limit size, and may drift independently; never clamp inconsistencies.
- **Grid rendering/cache**: exact page size equals complete data rows after all fixed rows in the assigned results area: its border, status/count line, and frozen header. Cache and metadata follow both lifecycle caps. Cells truncate at computed width with an ellipsis; tabs/newlines render as visible symbols; Unicode widths use a runewidth approach. Duplicate headers use the full-set deduplication rule. Horizontal state is a first-visible output-column index; each binding moves one whole column, recomputes widths, caps/ellipsizes an oversized column with no intra-cell scroll, and no-ops at boundaries.
- **Resize/layout**: for every supported H≥24, reserve exactly one bottom global status/help footer row. The builder's desired height includes its own border and padding, is capped at `floor(H/3)`, and internally scrolls to keep the full focused field/prompt visible. Assign every remaining row to results; that assigned area owns its border, status/count, header, and data rows and is greater than half of H. Each border belongs to exactly one region; overlays draw over regions and never reflow them. Resize recomputes exact page size, preserves/clamps the first-visible column index, and preserves the exact first logical row if retained/valid, otherwise clamps to a known endpoint or requests the containing page.
- **Invalid UTF-8 TEXT**: decode each maximal invalid byte sequence as exactly one U+FFFD consistently in grid, CSV, and JSON. BLOB handling is unchanged. Result metadata records that replacement occurred; the results header and export flow show a warning. Export succeeds, emits no extra warning records/fields, and retains row count/order.
- **Export formats and values**: CSV is RFC 4180 UTF-8 with CRLF, a header row, minimal quoting, and embedded tabs/newlines preserved in quoted fields. NULL and empty string both become an empty CSV field, an accepted lossy limitation. JSON is an array of objects: INTEGER/finite REAL are raw numbers using the exact integer/REAL tokens above, NULL is `null`, and non-finite pre-existing REALs are quoted `"Inf"`, `"-Inf"`, or `"NaN"`; CSV uses their textual form. BLOB retained bytes export exactly as lowercase hex CSV and base64 JSON and display `[BLOB n bytes]`. Computed/aggregate columns retain SQLite labels such as `COUNT(*)` before deduplication.
- **Output names**: walk left-to-right across the full original output-name set. First occurrence keeps its name; each duplicate gets the lowest `_2`, `_3`, etc. suffix not colliding with any already-final name, including original names. The same names appear in grid, CSV headers, and JSON keys; generated SQL and driver metadata are never altered.
- **History**: in-memory and session-only. Entries have stable IDs; each list retains 20 recent entries with oldest-first eviction. Query history stores complete field state; restore copies it into the builder and never mutates the entry. Append occurs only when an actual execution starts and is suppressed only when normalized state equals the immediately preceding execution: command, table, ordered projection, WHERE column/operator/value/bound type, GROUP BY order, ORDER BY/direction, Limit empty-vs-number, and UPDATE/INSERT choices and values. Thus A→B→A keeps both A entries. Entered representation, bound type, choice, and column order are significant. Starting execution exits history first. Defensive selected-entry eviction selects the new oldest, showing `Previously viewed result was evicted from history` for result history or `Previously viewed query was evicted from history` for query history; an empty list returns to base and evicted backing rows are never displayed. Result history stores immutable snapshots with retained positions, byte accounting, and all completeness/terminal/UTF metadata. Historical results never re-fetch; rerun gets fresh data. Snapshots re-slice to current terminal height when viewed.
- **Result export scope**: Ctrl+X is disabled during any request. At idle it captures an immutable instant copy of active rows and metadata before opening the picker, without finalizing the SELECT. Picker cancel or successful completion returns to the unchanged active result. Historical snapshots export identically. In terminal deletion/replacement, initial result selection is the most recent result-history entry; in outcome unknown, it is the newly appended outcome-unknown entry. Ctrl+E/Y changes that selected entry, and Ctrl+X always acts on the selection: a tabular snapshot exports, while an error, cancelled-before-rows marker, outcome-unknown entry, or other write summary reports `selected result has no tabular data to export` and opens no picker. To deliberately export a bounded subset, set Limit before execution.
- **Export warnings**: before destination selection/confirmation, the UI identifies complete, partial, and/or truncated state plus cancelled/failed and invalid-UTF information where applicable. These metadata/warnings never become CSV rows, CSV columns, JSON objects, or JSON properties.
- **Query save targeting**: one-way export only; loading is unsupported. Ctrl+S targets a viewed historical result's associated query; otherwise the current builder if runnable; otherwise the last actually executed query. If none exists, show inline `no runnable query to save` and do not open the picker. Terminal-state default is the last executed query, with Ctrl+P/N selection. Saved SQL is one standalone executable statement with identifiers double-quoted, strings quote-doubled, `NULL` keyword, BLOBs as `X'hex'`, and trailing semicolon.
- **File picker**: starts in working directory; displays directories including hidden ones and supports parent `..`; directory creation is unsupported. Directory selection and filename text entry are separate. Empty basename or basename containing `/` or NUL is invalid and shows inline error. Missing `.sql`/`.csv`/`.json` extension is appended. Esc cancels to the exact opener; permission/path errors stay inline for retry/cancel. Existing files require overwrite confirmation.
- **Atomic saves**: write a temporary file in the destination directory and rename it over the target. Serialization/I/O failure before rename preserves any existing destination and cleans the temp file. Temp-and-rename can itself fail under restrictive destination-directory permissions; this accepted limitation surfaces inline without claiming replacement occurred.
- **Schema scope, cache, and validation**: query `main.sqlite_master` only for ordinary tables, virtual tables, and views, excluding `sqlite_%` and `_cf_METADATA`. Views are SELECT-only; write command lists contain tables. Refresh object listing whenever Table opens and cache the resulting `PRAGMA schema_version`, object, column, eligibility, insertability, and rowid metadata. Enter on otherwise runnable data starts cancellable no-history validation by reading `PRAGMA schema_version`; unchanged uses cache, changed refreshes the selected object/columns and revalidates every identifier and capability. Invalid changes clear only dependent state and focus a specific reason. Lock/corruption/change failures show inline `could not refresh: …`, retain stale data with a notice, block execution, and offer retry/cancel; deletion/replacement overrides with terminal state. Post-validation DDL races are ordinary errors.
- **Schema metadata**: every object carries kind {ordinary-table, virtual-table, view}, rowid capability {has-rowid, without-rowid, not-applicable}, and declared-rowid-shadow flag. Columns carry name, declared type, and insertability from `PRAGMA table_xinfo`; hidden/generated columns are noninsertable. Declared type is metadata only and does not add type-specific v1 entry behavior.
- **INSERT handling**: prompt every insertable column; there is no AUTOINCREMENT-based skip. Each prompt offers Value/NULL/Default/Omit; Value opens text entry and empty is empty TEXT, NULL binds explicit NULL, and Default/Omit excludes the column. INTEGER PRIMARY KEY is prompted with `(auto-assigned if omitted)`. All prompted columns omitted emits `INSERT INTO "table" DEFAULT VALUES` through the normal execution path. A table with zero insertable columns shows `table has no insertable columns`, never enters prompts, and is non-runnable. Virtual tables are best effort using visible insertable columns; module failures requiring hidden inputs are ordinary query errors.
- **Builder lifecycle**: changing command retains only an eligible table, clears all downstream state, and focuses the first requirement. UPDATE assignments persist ordered {Value, NULL} choice plus Value text/bound type; revision and history restore both. Generated UPDATE parameters are Value assignments first in SET order and then WHERE. Popups/modals/text entry remain input-modal under the precedence table. Enter starts schema validation only when authoritative data and UI gates pass, and actual execution only after validation succeeds.
- **Keybinding portability**: bindings use terminal-distinguishable plain keys or Ctrl chords. No Alt or Ctrl+Shift binding is required because common terminals/multiplexers cannot distinguish or reserve them. `,`/`.` are reachable horizontal-scroll fallbacks when Shift+Page is intercepted. This PRD's context/action table is authoritative; there is no external key matrix.
- **Errors and cancellation bounds**: query errors replace results and create the lifecycle-defined single entry; Esc dismisses to the builder and older results remain. Count failure leaves rows/paging active with count error. Mid-scan or 64 MiB limit failure records the exact logical position. Save/path errors remain in save flow. Only startup failure, detected deletion/replacement, and resolved outcome-unknown end database work. v1 has no general query timeout, but controlled CPU-bound cancellation must settle within one second and lock-wait cancellation no later than the five-second busy timeout. Cancellation uses context plus connection-scoped interrupt, never force-close; late success is cancelled, and no replacement starts before settlement.
- **Logging**: none in v1—no debug flag or log file. Diagnostics stay in the TUI to avoid display corruption and sensitive query-value logs.

## Module Design

- **Connection**
  - **Responsibility**: owns discovery/opening, exact-two pool setup, dedicated leases, per-connection busy/length configuration, device/inode health checks, async context-plus-interrupt cancellation/identity, SQL plumbing, and transaction outcome resolution while hiding the pinned driver.
  - **Interface**: open-by-path with full validation/identity recording; open-D1 with exact discovery errors; cancellable `ReadSchemaVersion()`, schema refresh, independent `ExecutePage(query, offset, limit) → bounded rows/error-at-position`, `ExecuteCount(query) → count/error`, and `ExecuteEstimate(query, whereParams) → count/error`; phased transactional `ExecuteWrite(statement) → rowsAffected/definite-or-unknown outcome`. Concurrent page/count calls lease distinct connections; each request verifies path identity before work and after error, exposes request/interrupt identity and settlement, and never reuses a lease for replacement work before settlement.
  - **Tested**: unit tests with a controllable fake plus mandatory Linux/macOS SQLite integration and release-capability suites for journal overlap, configuration, cancellation latency/isolation/late results, identity replacement, limits, rollback, and commit boundaries.
- **Schema**
  - **Responsibility**: describes main-schema objects and columns independently of UI.
  - **Interface**: returns schema version and lists object kind, rowid capability, rowid shadowing, and columns with name/declared type/insertability; refresh failures are typed so UI can retain stale data and distinguish deletion/replacement.
  - **Tested**: table-driven catalog fixtures and SQLite integration tests for views, virtual/WITHOUT ROWID tables, shadowing, hidden/generated columns, refresh/drop, and zero-insertable tables.
- **QueryBuilder**
  - **Responsibility**: stores command-specific structured state (SELECT projection/WHERE/GROUP/ORDER/Limit, UPDATE assignments/WHERE, DELETE WHERE, INSERT ordered choices) and produces SQL plus bound params.
  - **Interface**: immutable get/set transitions; execution and exact destructive-estimate rendering; authoritative runnable report with first invalid field/reason; schema revalidation/only-dependent clearing; grouping/order rules; consecutive-history comparison. No UI dependency.
  - **Tested**: thorough pure tests, including identifier quoting, typed-NULL WHERE distinction, UPDATE Value/NULL choices and SET-then-WHERE parameter order, parsing/binding, grouping matrix, DEFAULT VALUES, changed-schema invalidation, and every runnable prerequisite.
- **UI**
  - **Responsibility**: Bubble Tea model for field bar, grid, popups, text entry, modals, file flow, global precedence/context table, exact quit suspension/restoration, validation/preparation/execution state machines, request/generation/settlement guards, serialized paging, dual-cap contiguous cache, stable-history selection, metadata warnings, deletion/replacement/outcome terminal states, and exact layout/column-scroll arithmetic.
  - **Interface**: Bubble Tea `Init`/`Update`/`View`, composing all other modules without embedding database behavior.
  - **Tested**: scripted `(model, msg) → (model, cmd)` behavior with fake Connection for transitions, popups, modal/quit precedence, history, errors, export, cancellation and late responses. Pixel/terminal rendering remains the specified manual matrix.
- **History**
  - **Responsibility**: two in-memory 20-entry stable-ID lists, navigation cursors, oldest-first eviction, consecutive-identical query suppression, selected-eviction fallback, and one immutable result snapshot per actual execution.
  - **Interface**: append/query/step/current-by-ID operations; no validation/preparation append; snapshots capped at 10,000 contiguous positions and 64 MiB retained payload with separate completeness and terminal outcome, endpoint/range/count/row-and-byte-eviction/failure/cancellation/UTF metadata.
  - **Tested**: yes, including both caps, consecutive-identical suppression and A→B→A retention, stable-ID eviction cursors, finalization/non-finalization events, metadata combinations, and terminal entries.
- **Export**
  - **Responsibility**: serializes an already immutable result copy to CSV/JSON and a query to SQL, then saves atomically.
  - **Interface**: result rows plus deduplicated columns and value policy; standalone query serialization; temp-and-rename path write. Completeness/outcome/UTF metadata drives UI warnings only and never alters data formats.
  - **Tested**: exact bytes for RFC 4180/JSON/SQL, value/name/invalid-UTF cases, and injected serialization/I/O/rename failures proving destination preservation.

## Out of Scope

- Any engine other than SQLite files/local D1 in v1, including PostgreSQL, MySQL, remote D1, and other remote services.
- Multiple simultaneous database targets or switching database files within one session; the two internal leased SQLite connections to one target remain required.
- Loading/importing saved queries or results; save/export is one-way.
- Persistence of query/result history or saved-file indexes across sessions.
- Free-text SQL entry and the post-v1 full-screen SQL editing mode; the application itself remains a full-screen TUI.
- Joins, subqueries, arbitrary expressions, IN, HAVING, AND/OR, parentheses, or multiple WHERE predicates.
- Frozen columns during horizontal scrolling; only the header row is frozen.

- Transactions spanning multiple user operations; the internal single-write transaction remains in scope.

## Acceptance Criteria and Supported Environment

- **Supported systems**: Linux and macOS; standard xterm-compatible key/arrow sequences; at least 16 colors; no mouse requirement. Some terminals intercept Shift+Page Up/Down, so `,`/`.` must provide equivalent horizontal scrolling.
- **SQLite support**: any SQLite 3-format database openable read-write by the exact pinned/vetted `modernc.org/sqlite`, including unchanged WAL and rollback-journal modes and local miniflare D1 files. Pure-Go/no-cgo builds are required.
- **Minimum terminal**: 80×24. Below it, show `terminal too small` instead of malformed layout, preserve all application state, keep `q` and Ctrl+C confirmation functional, and restore exact context/focus when resized back.
- **Automated definition of done**: all user stories and authoritative tables/lifecycles are implemented; unit, fake-Connection behavior, CLI, and SQLite integration suites pass, including every high-risk case. Mandatory journal/cancellation capability suites pass on Linux and macOS for every release and any modernc dependency upgrade; failure blocks release and requires changing the pinned version or implementation, not weakening behavior.
- **Manual definition of done**: complete the 80×24, 100×30, and 160×50 matrix and all listed resize/overlay/long-content scenarios, not only 80×24.
- **Visual invariants**: at every supported tested size H≥24, exactly one bottom footer row is reserved; builder desired border/padding height is capped at floor(H/3) with internal scroll; results receive every remaining row and exceed half-height; each border is owned once; overlays do not reflow; result fixed rows determine exact complete-row page size; horizontal state moves by one column and resize follows exact row/column preserve/clamp/fetch behavior.
- **Preparation/history invariant**: every schema-validation/preparation dismissal leaves both histories unchanged. Successful validation followed by actual execution appends query history subject only to consecutive-identical suppression; A→B→A remains. Each actual write and finalized SELECT produces exactly one stable-ID result, with defined selected-eviction fallback.
- **Transaction invariant**: beginning/executing accept cancellation; rollback cleanup/commit do not. Any cancelled/failed write described as untouched has confirmed rollback. Outcome unknown is terminal only after pending driver/transaction work has ended.
- **Connection/cancellation invariant**: page and count launch concurrently on distinct leases from an exact-two pool in WAL and rollback modes without journal mutation/hidden serialization. Every connection has five-second busy timeout and 64 MiB length limit. Cancellable requests show `cancelling…`, use scoped interrupt without force-close, reject late success, and satisfy the one-second CPU/five-second lock settlement bounds; writes preserve the pre-COMMIT cancellation flag and post-boundary noninterrupt rule.
- **Health invariant**: every request boundary/new connection verifies startup device+inode; absence and mismatch produce their exact terminal states, while same-inode mutation and the documented precheck race behave as specified.
- **Cache/export invariant**: cache never exceeds 10,000 contiguous absolute logical positions or 64 MiB retained payload, preserves duplicate-valued positions and exact BLOB bytes, handles row/byte overlap/eviction deterministically without partial rows, and exports retained rows ascending with truthful completeness/outcome/UTF/byte-truncation UI warnings.
- **Target envelope**: tables around 100,000 rows should be comfortable through paging, snapshots remain capped at both limits, and indexed first pages ideally render near 100 ms. These are guidance rather than definition-of-done performance guarantees; cancellation bounds remain mandatory.

## Further Notes

- The Connection abstraction preserves the broader multi-engine vision while v1 remains SQLite/local D1. Free-text SQL likewise remains deferred.
- First-page and count requests deliberately launch concurrently on two distinct leased connections without changing WAL/rollback journal mode. They can drift or be delayed by writers; `Result count` is the independent count of the complete SELECT including Limit, not table/pre-limit size or an exact shared snapshot total.
- Cancellation is a vetted pinned-driver capability, not best effort: cancellable contexts plus connection-scoped interrupts, visible settlement, no force-close, bounded controlled cases, and mandatory Linux/macOS release/upgrade tests enforce the contract.
- UPDATE deliberately offers Value/NULL but not Default/Omit. Typed `NULL` in WHERE remains TEXT; contextual guidance directs SQL-null intent to `IS NULL`/`IS NOT NULL`.
- Finite REAL output uses one shortest-round-trip, REAL-preserving token across grid, CSV, and JSON. The dual row/byte cache limits keep eager TEXT/BLOB browsing bounded and disclose byte truncation rather than pretending to stream LOBs.
- Device/inode verification distinguishes deletion from same-path replacement at operation boundaries. Schema-version validation then protects runnable builder state without claiming to eliminate a post-validation DDL race.
- `q` and Ctrl+C intentionally share confirmation in all nonterminal enabled contexts; exact estimate/overwrite suspension avoids accidental destructive-flow loss. Terminal deletion/replacement/outcome-unknown remains immediate status-1 because no work is pending.
- The aggregate/GROUP BY rule prevents SQLite's arbitrary bare-value behavior in every grouped query, including nonaggregate-only projections; wildcard GROUP BY is therefore prohibited.
- The internal transaction provides an untouched guarantee only after rollback is confirmed. SQLite FAIL/trigger behavior motivates the wrapper, while the explicit commit boundary and outcome-unknown state avoid promises the driver cannot prove.
- Destructive matching-row estimation is independent and non-binding: it counts the quoted target under the identical WHERE predicate, not trigger effects, actual changed rows, or no-op differences.
